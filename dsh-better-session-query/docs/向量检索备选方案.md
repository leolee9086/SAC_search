## 一、三个可复用对象（事实，均已读源码核实）

### 1. s-forge `packages/vectordb`（Go，现役实现）

- 位置：`D:\dev\s-forge\packages\vectordb\`（`docs/ttt/vectordb/backups/...` 是历史快照，**不是现役**）。
- 包结构：根包（统一 DB 入口/集合句柄/持久化）、`hnsw`（内存图）、`vamana`（Vamana 与 DiskVamana 磁盘图）、`bbq`（二值量化与评分）、`storage`（磁盘读取器、mmap、序列化、删除位图）。
- 公开 API：`Open(path)`、`CreateCollectionWithOptions(name,{Engine,Dimension,DistanceMetric})`（`EngineDiskVamana` 主引擎 / `EngineHNSW`）、`OpenCollection`、`DeleteCollection`、`ListCollectionStats()`、`CollectionHandle.Write(ctx,batch,{durability:memory|async|sync})`、`Checkpoint(ctx)`、`Upsert/Search/Delete/Flush/Stats/Close`。距离：`l2`/`cosine`/`ip`（cosine: score = 1 − distance/2）。
- 工程特性：提交序号线性化、CRC32C WAL 帧、`recovery-required` 恢复态、Windows 上 WAL 回滚先关 `O_APPEND` 句柄再截断、DiskVamana 用原生 graph remap 合并"磁盘图+append 区+删除位"并原子切换 generation manifest、后台 checkpoint、目录级跨进程独占锁、快照主/次版本与未知必需特性位拒绝。
- **BBQ 方案（用户称为"已知最优"的那部分，实际措辞见下）**：非对称 **query 4-bit × data 1-bit**，生产契约固定（`vamana/constants.go:114`、`disk_index.go:763` 注释"保留兼容入口；生产契约固定为 4-bit query × 1-bit data"）；查询走 4-bit **BitTranspose** 布局（`bbq/asymmetric.go`），距离用**位平面转置 + POPCNT 点积**（`bbq/bitops.go`：`PackBitTranspose4`/`ComputeTransposedDotProductWords`）；**每向量 1 个 float32 补偿项**（`vamana/bbq_test.go:444`：`bbqPackedSize bytes + 4 bytes (compensation float32)`）；量化网格 `MinMSEGrid`（`bbq/constants.go:43`，均匀分布下的 MSE 最优区间）。源码定位语："非对称量化是 SOTA 高精度路径（参考 `toread/rust-bbq`：index_bits=1, query_bits=4）"（`vamana/disk_bbq_search_test.go:9-10`）。
- **磁盘占用（768 维/向量）**：f32 3072 B → f16 1536 B → i8 768 B → **1-bit 码 + f32 补偿 = 100 B（≈31× 压缩）**；无训练（data-oblivious，1-bit 即符号、4-bit 是网格），因此**支持增量插入**（PQ/OPQ 做不到）。
- 两段式检索契约：粗排取 `topK × bbqRerankFactor` 候选，再全精度精排（`vamana/disk_search.go:176`、`vamana/bbq.go:192-244`）。
- 已有测量口径：`ann_benchmarks_test.go`（Recall@10/QPS/p50-p95-p99）、`bbq_4bit_comparison_test.go`（1-bit vs 4-bit × OSF 1/2/3/5）、`bbq_benchmark_test.go` 的优化前基线（4-bit OSF=5 召回 98.20%@4244µs、OSF=3 96.10%@2973µs、OSF=2 92.50%@2058µs）、与固定 USearch v2.22.0 的**逐查询交错对照**（checkpoint 后 QPS 中位比值 ≈0.63(ef32)/0.76(ef200)，Recall@10 98.8%/100%）。
- **没有 npm/WASM/JS 产物**：无 `package.json`、无 `.js/.ts/.wasm/.node`；`go.mod` 只依赖 `msgpack/v5` + `golang.org/x/sys`。对外绑定只有 `//go:build mobile` 的 gomobile 与对 USearch 的 C ABI 对照（基准用）。

### 2. `D:\dev\gpuSort`（WebGPU 基础排序库，用户自写；**不在 s-forge 里**）

- 源码树（已全读，排除 node_modules）：
  `src/kernel.js`、`src/index.js`、`src/webgpu/{index.js,webgpu-init.js,bitonic-sort.js,bitonic-sort.wgsl}`、`src/webgpu/channeledSort/{index.js,channeled-sort.wgsl}`、`src/cpu/{index.js,cpu-sort.js}`、`common-utils/{constants,math-utils,array-utils,index}.js`。
- 入口：`WebGPUSort.init()` → `bitonicSort(keys, values?, options)` / `cpuSort(...)` / `sortRaw(...)`（返回 ArrayBuffer 形状）/ `sort(...)`；按 `GPU_CPU切换阈值` 自动分流（大数组走 GPU，小数组走 CPU）。
- **KV 的语义（已更正）**：这是**基础算法库**，**不做打包**——打包是调用方的事。`values` 参数在 CPU 路径做完整键值对置换（`common-utils/array-utils.js` 的 `创建键值对数组`/`提取键值对`）；GPU 双调路径只排 `keys`（wgsl 只有 keys+params 两个绑定，现役与 backup 都一样），**这不是漏绑**：调用方把身份打包进 key，排完的 key 数组自带 id，value 在 JS 内存侧取回。
- `channeledSort`：多通道平铺数据 `[R1,G1,B1,R2,G2,B2,…]`，按 `sortChannels` 位掩码**逐通道独立排序**（提取单通道 → 双调 → 写回同一通道槽位），兄弟通道按设计不动（其头注释原文："对 R 排序，G 和 B 不会被移动"）。三个绑定 `data/channel_data/params`，`operation` 枚举 0=提取 1=排序 2=写回。
- 性能（用户实测口径）：**排序算法本身 GPU/CPU ≈ 60×，综合（端到端）≈ 40×**。
- 注意：排序是 O(n log²n)，全排序 n=2^k 需 **k(k+1)/2** 个 pass（20 万元素 = 171 个 pass）→ **top-k 场景应先做阈值/分位筛选，只对候选排序**，而非全量排序。

### 3. USearch（对照物）

- 自报能力表里**只有 HNSW 家族**（无 DiskANN/Vamana）；`view()` 是把 HNSW 索引 mmap 起来服务，**不是磁盘常驻图**。
- 量化是**对称降精度**（f64/f32/bf16/f16/fp8/fp6/u8/i8/`b1x8`），README 明确：`b1x8` 只对 Jaccard/Hamming 等**二值度量**有效、量化后**取不回原向量**——没有"1-bit 粗筛 + 全精度重排"的补偿机制。
- 持久化只有 save/load/view，**无 WAL、无 checkpoint/代际、无跨进程锁、无恢复态**。
- 优势：SIMD/JIT 绝对速度、**10 种语言绑定（含 npm `usearch`）**、多平台预编译、成熟度；且 s-forge 自己把它当基准对照。
- 结论：**不是同等能力**；缺的正是 DiskANN/Vamana、非对称 BBQ + 补偿、事务性持久化三块。

## 二、接入方式备选（四条，代价从低到高）

| 方案 | 做法 | 代价 / 约束 |
|---|---|---|
| **A. Go exe sidecar + stdio** | 用 s-forge `packages/vectordb` 编一个 exe，JSON/stdio（或 JSON-RPC）协议，插件 spawn 它 | **常规做法**（LSP/rg 包一层都这么干）；代价＝进程启动(~10–50ms) + IPC + 崩溃重启/背压 + 每平台二进制（~15–30MB）。**不需要 CGO/FFI**，跨平台最稳 |
| **B. c-shared + N-API/FFI** | `go build -buildmode=c-shared` 出 `.dll/.so`，再 N-API 或 koffi 调 | 延迟最低，但要维护各平台预编译产物（sharp/usearch 那套），构建链最重 |
| **C. WASM** | Go 1.25 编 `wasip1` | 无需原生构建；但 **DiskVamana 走 mmap/`golang.org/x/sys`，基本过不去**，能过的多半只有内存 HNSW |
| **D. 重实现（调用方侧）** | 只搬**方案**不搬代码：BBQ 编码/距离 + 你的 `gpuSort` 排序 + 精确重排 | 无跨语言负担、无原生构建；但要自己承担正确性与基准。**当前倾向**（见下） |

## 三、调用方侧流水线设计（方案 D 的具体形状）

1. **编码/落盘**：每块向量 → 1-bit packed data code（`dim/32` 个 u32）+ 每向量 1 个 f32 补偿项；码与"原向量/降精度向量"分别落 SQLite BLOB（精排时才按 id 读原向量）。
2. **查询侧编码**：查询向量 → 4-bit BitTranspose（照 vectordb 的方案：4-bit query × 1-bit data + 补偿）。
3. **打包（调用方约定，库不管）**：`key = (量化距离 << 18) | 块序号`（20 万块用 18 位；距离留 14 位桶即可，桶内不逆转由精排收口）；或 `vec2<u32>` 字典序做精确比较。
4. **距离 kernel（另写，不在 gpuSort 内）**：对全部码算 POPCNT 距离 → `Uint32Array`。这是**内存带宽瓶颈**（19MB/查询 @20 万块），不是排序瓶颈。
5. **top-k**：先**阈值/分位筛**出候选 m ≪ n，只对 m 调 `WebGPUSort.sort(packedKeys)`，解出 id。
6. **精排**：按 id 读原向量（几百候选 ≈ 几百 KB/查询）算精确距离，返回 topK。
7. **降级路径**：CPU 版同构实现（`Uint32Array` popcount 全表扫），用于无 WebGPU 环境与正确性对照。

**部署位置（必须先定的岔口）**：WebGPU 在**客户端**（浏览器/Electron 渲染进程），DSH 插件宿主半边是 **Node（无 WebGPU）**。
- A：检索跑在插件**客户端半边**（页面里），码表经 loopback 路由下发 → 零原生依赖，多一次 IPC + ~19MB 显存常驻；
- B：宿主侧 **wgpu-native/Dawn sidecar** → 无浏览器依赖，但回到每平台原生构建；
- C：宿主侧**纯 CPU** → 最简，延迟几十 ms 级。

## 四、待实测的指标与已知缺口

- **精度**：粗排距离是近似的 → 必须用 **Recall@10 vs 精确暴力** 定"放大因子/OSF + 精排深度"，并在**真实会话块向量**上量（不是 SIFT）。搬运的是口径（`ann_benchmarks_test.go`、`bbq_4bit_comparison_test.go`)，不是代码。
- **延迟**：端到端（含 GPU 上传/回读）与纯 CPU 对照；排序段收益（用户实测 60×/40×）**不等于**整链收益。
- **缺口 1：embedding 来源**。s-forge 的 vectordb 刻意不含 embedding（README 边界禁止 import Embedding 包）；DSH 侧我**尚未确认**有可用 embedding 通道。**没有 embedding 就不该先建向量索引。**
- **缺口 2：WebGPU 位置**（见第三节岔口）。
- **不需要的东西**：WAL、原子代际、manifest、跨进程锁——本插件的索引库是**派生库**（可从会话日志重建），那套持久化对我们是纯负担。
