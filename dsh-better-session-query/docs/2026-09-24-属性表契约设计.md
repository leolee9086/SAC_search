# 会话属性表（attribute）契约设计

2026-09-24。哥哥定的范式 + 一路讨论下来的结论。**本文只写设计，未实现。**

## 一、范式

> **索引插件存在就存索引插件里，不存在就在进程内维护。**

这是**之后很多类似内容的通用范式**，不是为 context-care 一家做的。

推论：属性表是**通用存储**，不预设业务语义；业务属性名与 value 形状由各写入方自己定。

## 二、为什么不做 npm 包（schema 库）

DSH 里插件之间共享只有一条路：**运行时服务契约**（`ctx.get()` / `inject`）。
静态 import 别人的值会破坏插件独立性（装不上、改个枚举要跟着发版）。

一个“只有常量和类型”的包技术上是合法的，但它能提供的恰好是编译期依赖 —— 而那正是插件架构不允许的那一类。

所以契约分三层，各归其位：

| 层 | 谁定 | 载体 |
|---|---|---|
| 存储层 schema（表结构、四个方法、软删语义、schema 版本） | 索引插件 | 它自己的 `STORE_SCHEMA_VERSION` + 服务方法签名 |
| 命名空间清单（表里现在有哪些 namespace） | 服务运行时回答 | 挂在服务上，消费方运行时读 |
| 各 namespace 的属性名与 value 形状 | 各 namespace 的主人 | 各自的文档 |

一致性不靠共享库：**持久实现只有索引插件一家**，**进程内实现是消费方自己的代码**，不存在两套要对齐的实现。
分支只出现在**取服务那一处**。

## 三、表结构

```sql
CREATE TABLE IF NOT EXISTS attribute (
  id          TEXT PRIMARY KEY,      -- uuid：同一位置可以挂任意多条（标记天然是多条）
  session_id  TEXT,                  -- NULL = 不属于任何会话（全局属性）
  seq         INTEGER,               -- 事件级定位
  block_index INTEGER,               -- 事件 message.content 数组下标
  from_pos    INTEGER,               -- 该块文本内字符偏移起点；NULL = 整个块
  to_pos      INTEGER,               -- 终点
  namespace   TEXT NOT NULL,         -- 谁写的
  name        TEXT NOT NULL,         -- 属性名，任意 Unicode
  value       TEXT NOT NULL,         -- JSON
  origin      TEXT NOT NULL,         -- 'plugin' | 'user' | 'model'
  visibility  TEXT NOT NULL,         -- 'private' | 'user' | 'model'
  created_ms  INTEGER NOT NULL,
  updated_ms  INTEGER NOT NULL,
  deleted_ms  INTEGER                -- 软删；NULL = 有效
) STRICT;
CREATE INDEX IF NOT EXISTS idx_attribute_target ON attribute(session_id, seq, block_index);
CREATE INDEX IF NOT EXISTS idx_attribute_ns     ON attribute(session_id, namespace, name);
```

### 为什么主键是 uuid 而不是 (session_id, namespace, name)

后者是**键值属性**模型（一个位置一个名字只能一条），而“做标记”天然是**多条**（一条回答里标三处就是三条），用那个主键会互相覆盖。

### 为什么定位不用 block_meta.path

`path` 是**索引层算出来的**（派生数据），而索引可重建：schema 版本一升整表 DROP 重来，切块规则一变 path 就跟着变。
用 `path` 当持久定位 = 把标记钉在一个随时会被重算的坐标系上。

而**事件内容是不可变的**（append-only），所以 `(seq, block_index, from_pos, to_pos)` 四个字段全落在不可变数据里 ⇒ **永久稳定**。

`path` 降级为查询时现算（要 JOIN 块索引时用 `(seq, block_index)` 对上），**不落库**。

### 关于“被屏蔽的内容”

两类，都不需要特殊字段，但要求定位维度是通用的、不预设“内容一定在表层”：

1. **被屏蔽的内容本身**（`log-only` / `shadowed`，不在当前表层）—— 标记要能落上去。所以写入时**不得**去查表层、不得拒绝非 surface 节点。
2. **“这段被屏蔽了”这件事** —— 它本身就是一条属性（`name` 记类型、`value` 记原因和范围）。

### 与块索引的坐标系关系

块索引也是 `(session_id, seq, path)` 三维，所以标记能 JOIN 到具体块上。但那是**查询时**的事，不影响持久定位。

## 四、DOM 名映射（Unicode 折衷）

思源的 `attributes` 表把 `name` 直接当 DOM 名用（`custom-xxx` 渲染成 HTML 属性、前端用 `dataset` 读），所以名字被 DOM 字符集绑死。
**存储层本来自由，是渲染层的需要反过来限死了存储层** —— 我们不这么干。

拆开两个名字：

```
存储/语义层              渲染层
name: 任意 Unicode  →  domName(): 纯函数投影  →  合法 DOM 名
```

映射规则（确定性、可逆、无歧义）：

- 只保留 `[A-Za-z0-9]` 原样；
- **其余每个字符**（含 `_`、`-`、空格、中文、emoji）→ `_x` + 码点十六进制 + `_`；
- `_` 自己也转义 ⇒ 转义序列的 `_` 不会与原文的 `_` 撞；
- 前面接 `data-attr-<合法化的 namespace>-`。

例：`循环清理` → `data-attr-context-care-_x5faa__x73af__x6e05__x7406_`

**这一列不存** —— 它是纯函数，存了反而会不一致（思源那种“存的就是渲染用的”正是问题来源）。
将来真要渲染时现算，规则钉在本文里两边共用。

## 五、STORE_SCHEMA_VERSION 与 OWN_TABLES（关键坑）

索引插件的 `openStore()` 在版本不匹配时：

```js
for (const name of tables.filter(t => OWN_TABLES.includes(t) || t.startsWith("block_fts"))) {
  db.exec(`DROP TABLE IF EXISTS "${name}"`);
}
db.exec("PRAGMA user_version = 0");
```

块索引是**派生数据**（能从会话日志重建，所以敢 DROP）；属性表是**原始数据**（丢了不可重建）。

⇒ **attribute 要加进 `ensureSchema`，但不加进 `OWN_TABLES`**。这样版本升级时它被跳过，块索引照常重建。

这一条是整件事的关键。

## 八、与 context-care 的关系

context-care 是第一个消费方（改写/清理记录、变换记录），但**不是定义者**。
它的用法：改写命中 → `ctx.get(...)` 拿服务 → 有就持久、没有就用自己的内存表；UI 侧只拿 `(seq)` 查表，**不跑规则**。
