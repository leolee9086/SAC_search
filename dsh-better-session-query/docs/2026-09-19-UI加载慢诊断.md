# UI 加载慢：根因是 monitor 快照每秒做两遍全表扫描（2026-09-19 深夜）

## 一句话

**修好 404 之后变慢，是因为路由终于开始干活了 —— 而它每 1000ms 干一次、每次要 2.6 秒。**
不是索引大小的问题，是 `store.size()` 这个查询本身随正文总量线性增长，而它被调了两遍。

## 实测数字（全部真跑出来的）

### 端点响应时间

| 端点 | 第一次 | 第二次 |
|---|---|---|
| `/session-blocks/monitor.json` | **2844ms** | **2630ms** |
| `/session-blocks/memories.json` | 4ms | 2ms |

**只有 `monitor.json` 慢**，`memories.json` 很快 —— 所以问题在快照组装，不在记忆库。

### monitor 快照的分解（动态插件探针实测）

| 部分 | 耗时 |
|---|---|
| `svc.stats()` | 86ms / 93ms |
| `listSessions()`（会话清单） | 1406ms / 1313ms（但插件侧有 60 秒缓存，正常路径不常跑） |
| `monitor()` 整体 | 3977ms |

### `store.size()` 内部逐条计时

| 查询 | 耗时 |
|---|---|
| `COUNT(*) FROM block_meta` | 10ms |
| **`COUNT(*) FROM block_fts`**（FTS5 虚拟表） | **568ms** |
| **`SUM(LENGTH(CAST(text AS BLOB))) FROM block_fts`** | **626ms** |
| `SUM(LENGTH(CAST(text AS BLOB))) FROM block_text` | 73ms |

`block_fts` 是 FTS5 虚拟表，`COUNT(*)` 要遍历整个倒排索引；`SUM(LENGTH(CAST(text AS BLOB)))`
要把 526MB 正文整个读出来量一遍。**这两条就占 1.2 秒。**

## 根因链（闭合）

```js
// lib/index.js:876-887  monitorSnapshot()
stats: opened.store.stats(),
size: opened.store.size(),                    // ← ① 1.3 秒
needsCompact: opened.store.shouldCompact(),   // ← ② 内部又调 this.size()，再来 1.3 秒

// lib/store.js:869-871
shouldCompact() {
  const current = this.size();   // ← 第二次全表扫描
  return current.dbBytes > Math.max(4 * 1024 * 1024, current.textBytes * 1.6);
}
```

**一次快照 = 两遍 `size()` ≈ 2.6 秒**，与端点实测的 2630/2692/2844ms 完全吻合。

而 `lib/monitor.js:246` 是：

```js
const timer = setInterval(push, 1000);   // SSE 每 1000ms 推一次
```

**生产 2.6 秒 > 消费间隔 1.0 秒** —— 请求永远追不上，永久积压。
`body === lastBody` 的去重只省网络传输，**省不了组装成本**（组装在比较之前）。

## 为什么是"修好 404 之后"

404 的根因（见 `2026-09-19-监控404根因与monitor重构.md`）：`monitor.js` 用了急切的
`ctx.get("webServer")`，而 webServer 比本插件晚加载 → 路由从来没挂上 → **以前是立刻 404 返回**。

改成 `ctx.inject(["webServer"], ...)` 延迟取得后，路由真的挂上了 ——
于是这个每秒 2.6 秒的成本**第一次真正开始被支付**。

## 与索引大小的关系

**没有直接关系**。用户判断正确：不是库变大了才慢。
`size()` 的成本**随正文总量线性增长**，所以它一直会随索引推进而变慢，只是以前 404 掩盖了它。

（顺带：另一个独立问题 —— 39 个 fork 子会话每 30 分钟重试一次、每次白烧 5 秒，
根因是 DSH 的 seed 不变量 `inheritedEventCount !== log.length`。**那是索引速度的问题，
不是本次 UI 加载慢的原因**，别混在一起。）

## 修法（待定）

按哥哥的原则「不要兜底值，宁可报错」以及「别为翻页再算 COUNT」的既有结论：

1. **`shouldCompact()` 别自己再调 `size()`** —— 让调用方把已经算好的 `size()` 传进去。
   这一条直接砍掉一半（1.3 秒）。
2. **`size()` 里的全表扫描不该放在热路径**：
   - `COUNT(*) FROM block_fts` 是 FTS5 虚拟表遍历，可以改用 `block_meta` 里已知的可检索块数
     （`searchable` 计数，写入时维护）。
   - `SUM(LENGTH(CAST(text AS BLOB)))` 要遍历 526MB 正文 —— 这是"统计展示"用的数字，
     应该缓存（几秒~几分钟），或者改成从 SQLite 页计数近似（`dbBytes` 已经有了，本来就是 O(1)）。
3. **SSE 推送不该"每秒重新组装"**：应该事件驱动（`lastSummary` / 索引进度变化时才重算），
   或者至少把间隔调到远大于组装成本。
4. **组装成本必须实测**：这次能定位是因为最后量了每个部分；
   光看代码不会发现 `shouldCompact()` 里藏着第二次 `size()`。
