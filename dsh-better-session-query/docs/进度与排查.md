## 二、正在排查的问题：进度长时间停在 111

### 根因（已用数据确认，2026-09-15 23:2x）

`lib/indexer.js` 的 plan 只有一条排序规则、且实时会话无条件"到期"：

```js
function needsCheck(item, indexed, now, force) {
  if (force) return true;
  if (item.live) return true;                       // ← 实时会话每轮都到期
  if (indexed === undefined) return true;
  return now - checked >= config.recheckMs;         // 冷会话 600s
}
...
plan.sort((a, b) => Number(b.live) - Number(a.live));   // ← 实时会话永远排在头部
const batch = plan.slice(0, limit);                     // limit = 25
```

**只要实时会话数 ≥ 25，每轮 batch 就是这同一批实时会话**，它们已索引 → 更新 0、未变 N，而 1378 个未索引会话永远排在它们后面、轮不到。

实测证据（`session_blocks_sql`）：

- 已索引 111 个会话里**只有 36 个 TTL 到期**（75 个在 600s 内刚复查过）；
- 已索引会话的时间跨度是 **14 天**（最老 `1788268521217`、最新 `1789484871829` ≈ 66 秒前）→ 不是"只索引了最新的"，排除"只扫头部最新会话"这一层；
- 面板一轮的形态恒定是 `更新 0 / 未变 13~25`，即 batch 全落在已索引会话上 → 只有"实时会话每轮到期 + 排在头部"能解释这个恒定性。

（我最初的假设是"TTL 到期的会话挤占名额"，数据否掉了一半：36 个到期会话复查完就会离开到期集合，不会每轮恒定占满 25 个名额。）

### 修法（下一步实施）

1. **每轮给"从未索引"的会话保留至少一半名额**（backlog 非空时）：
   `reserve = max(1, ceil(limit/2))`；batch = `backlog.slice(0, reserve)` + `fresher.slice(0, limit - reserve)`，其中 fresher 内部仍按 live 优先、新的在前；
2. **失败会话加冷却**（默认 30 分钟，内存 Map）：`needsCheck` 对读不出来的会话每轮恒真，那 8 个坏会话每轮白吃名额，冷却掉；
3. 摘要里补 `backlog / live / due` 三个计数（面板与状态工具可见），下次再出这种事一眼看得出来；
4. 验证：重启后看覆盖率是否持续爬升、`待索引` 数是否下降。

### 次假设（保留观察）

- 单轮成本高（每会话 2 次整段日志装载：`listEvents` 算指纹 + `readSession` 读正文），25 个/轮可达 100 秒级——解释"很久不动"的观感，但不是根因（根因是选谁进 batch）；
- 根治仍是侦察结论里的「脏集合 + 便宜令牌」（见第六节待办 2）。

## 八、surface 兜底值修复（2026-09-19 23:1x）

**症状**：`session_blocks_remember` 写完立刻 `session_blocks_recall`，会把自己刚记的那条「想起来」一次 ——
本该被「已经在活跃上下文里就不再返回」的规则挡掉。

**根因**（`lib/blocks.js` 的 `buildSessionBlocks`）：块列表由两次独立读取合成 —— `listEvents` 给 surface、
`readSession` 给正文，按 seq 对齐。索引器分两相读（compare 取 `listEvents`、write 取 `readSession`），
之间会话继续写入，于是 events 里多出来的新 seq 在 records 里没有 surface，**原来的代码把它兜底成 `log-only`**。
下游记忆召回正是按 `surface === "current"` 判断「这条是否还在眼前」，一个假的 log-only 让判断整个反过来。
下一轮 records 追上后差量更新把 surface 改成 current，所以现象只持续 ≤30 秒（`backgroundReconcileMs`）。

**排查证据**：

| 环节 | 结果 |
|---|---|
| 动态插件探针实测 `exec.agent.session.id` | `session-354f0d20-…`，与 `memory.session_id` **完全一致** → 排除 id 对不上 |
| 同一组关键词第一次 recall | **返回了**那条记忆 |
| 隔几分钟第二次 recall | **「候选 1 条、返回 0 条」** → 索引追上后过滤生效 |
| 采样器每 5s 观测 `memory` 表 | 那条记录的 `surface` 事后是 `current` |

**修法**（不给默认值）：

- seq 比 records 里最新 seq 还大（＝这次读取之后才写进来的）→ **跳过不产出**，等下一轮 records 追上再索引。
  指纹 `eventsRevision` 取自 records，所以下一轮必然重跑，不会漏。
- seq 落在 records 范围内却缺 surface → **直接抛错**（两次读取对不上，不该替调用方猜）。

**验证**：`node --test` **147 pass / 0 fail**（`blocks.test.mjs` +2 条：跳过新块、范围内缺 surface 抛错）。
profile 的 revision 已 bump 为 `surface-skip-1`。

**顺带纠正**：`cordis.patch.yml` 里那行是带 revision 的 `file://` 行，bump 它即可热重载
