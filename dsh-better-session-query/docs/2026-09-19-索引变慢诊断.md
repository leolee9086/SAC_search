# dsh-better-session-query 索引变慢：诊断（2026-09-19 23:3x）

## 结论先说

两个独立的慢，都是**固定开销随「会话/块总量」增长**，不是库变大本身：

| 现象 | 根因 | 量级 |
|---|---|---|
| **索引速度慢**（0.1/s） | 39 个**读不出来的会话**每 30 分钟重试一次，每次白烧约 5 秒 | 每轮 ~195 秒 |
| **界面加载慢** | 面板 SSE **每 1000ms 全量组装一次快照**，其中 `stats()` 做 4 个全表 COUNT（`searchable=1` 是全表扫描） | 每次 ~100ms+，每秒一次 |

## 一、索引慢：坏会话反复重试

### 证据

动态插件探针直接计时（`ctx.get('sessionQuery')`）：

```
坏会话 session-00e4f347-…：
  listEvents:            2380ms (n=2841)
  readSession:           抛错 2447ms — seeded session constructor seed must equal its inherited prefix
正常会话 session-354f0d20-…：
  listEvents:             227ms (n=2682)
  readSession:            888ms (n=2682)
```

**同样约 2800 事件，坏会话的 listEvents 是正常会话的 10 倍**（2380ms vs 227ms）。

日志统计：

- `失败:seeded session constructor seed must equal its inherited prefix` 共 **4818 次**
- 涉及 **39 个唯一会话**
- 同一会话的重试间隔是 **30 分钟**（＝ `recheckMs` 到期复查，不是每 30 秒）

**所以冷却机制（`failureCooldownMs` 默认 30 分钟）在正常工作** —— 30 分钟正好等于 `recheckMs`，
于是冷却一到期就又被复查选中，再烧 5 秒。39 × 5s ≈ **每 30 分钟 195 秒纯浪费**。

### 为什么这些会话读不出来

DSH 的不变量（`packages/core/session/src/index.ts:608-609`）：

```js
if (mode === 'snapshot' && this.header.isSeeded && inheritedEventCount !== this.log.length) {
  throw new Error('seeded session constructor seed must equal its inherited prefix')
}
```

这些是被 seed（fork）过的会话，`inheritedEventCount` 与实际日志长度对不上。

### 为什么它们比正常会话慢 10 倍

坏会话目录里有 **5 个世代的文件**：

```
session.jsonl.zstd                  2.66 MB
session.jsonl.zstd.websearch-…      2.66 MB
session.v2.jsonl.zstd               2.38 MB
session.v2.jsonl.zstd.websear…      2.38 MB
session.v3.jsonl.zstd               2.38 MB
```

正常会话只有 `session.v3.jsonl.zstd` 一个。读的时候要跨世代装载/合并，成本就上去了。

**注意**：`session-blocks.log` 的 `慢会话` 行报的是 `令牌 0、轻量 0、正文 1459ms` ——
令牌路径与轻量路径都是 0，说明**时间全在装载正文**，符合上面这个解释。

## 二、界面加载慢：面板每秒全量组装快照

`lib/monitor.js:246`：

```js
const timer = setInterval(push, 1000);   // SSE 每秒推一次
```

`push` 每次都 `JSON.stringify(await deps.snapshot())`，而 `deps.snapshot` = `monitorSnapshot()`
（`lib/index.js:876-887`）每次组装：

```js
stats: opened.store.stats(),        // 4 个全表 COUNT
size: opened.store.size(),          // 文件大小
listed: await countListedSessions(),// 会话清单
walBytes: fileBytes(...),
needsCompact: opened.store.shouldCompact(),
```

`store.stats()`（`lib/store.js:936-940`）的四个 COUNT 实测：

| 查询 | 耗时 |
|---|---|
| `COUNT(*) FROM block_meta` | 9ms |
| **`COUNT(*) FROM block_meta WHERE searchable = 1`** | **79ms**（全表扫描，随块数线性增长） |
| `COUNT(*) FROM block_text` | 5ms |
| `COUNT(*) FROM indexed_sessions` | 0ms |

`body === lastBody` 的去重**只省网络传输，省不了组装成本** —— 每秒都在跑这 4 个 COUNT。

## 三、建议（待哥哥定）

1. **坏会话**：39 个会话永远读不出来，每 30 分钟白烧 195 秒。要么把它们的失败也计入一个
   **比 recheckMs 更长的永久冷却**（区分「读不出来」与「还没到期」），要么在日志里降噪后
   明确接受这个成本。根子在 DSH 的 seed 不变量，本插件只能选择怎么对待。
2. **面板快照**：`stats()` 的结果不需要每秒重算。缓存几秒，或者改成事件驱动
   （只在 `lastSummary` 变化时重算），把 SSE 变成"推变化"而不是"每秒重新算一遍"。
3. **全表 COUNT**：`WHERE searchable = 1` 可以改成维护一个计数器（写入时增减），
   或者只在面板真的展示时才查。
