## 已实现 5（独立复现）：FTS 行号对齐 —— `block_meta(fts_rowid)` 索引 ✅

**优化点**：让"倒排命中 → 回表取元数据"这一跳走索引，而不是落在没有索引的裸列 `block_meta.fts_rowid` 上。s-forge 的做法更彻底——`kernel/sql/database.go:300` 用 `content='blocks', content_rowid='rowid'` 把倒排行与内容行绑成同一个 rowid（`:299` 注释：所有写路径必须显式传 rowid，否则 snippet 回表取错行、按 rowid 删除静默失效）。

**落地现状**：`lib/store.js` 已有 `CREATE INDEX IF NOT EXISTS idx_block_meta_rowid ON block_meta(fts_rowid)`（**非唯一**索引，所以它担心的"历史库有重复 fts_rowid 会建索引失败"不成立），`bench/search-bench.mjs` 做开/关对比。**不需要 bump schema 版本、不需要重建索引**：老库下次打开就地建。

**独立实测**（24,000 块 / 40.3MB **真实正文**——本机 17 个真实 `session.jsonl.zstd` 解开、经 `lib/blocks.js` 抽块；SQL 用 `search()` 原样）：

| 场景 | 加索引前 | 加索引后 | 倍数 |
|---|---|---|---|
| 高频词 `import`（命中 3,071 块） | 24,141ms | **27ms** | ≈900× |
| 稀疏词 `store.js`（命中 4 块） | 39.0ms | 2.1ms | ≈19× |
| 库体积 | 63.9MB | 64.1MB | +0.4% |

计划从 `SCAN m` 变成 `SEARCH m USING INDEX idx_block_meta_rowid`。稀疏查询那 19× 是每次检索都吃的固定开销——这是比"高频词 900×"更重要的数字。

**未采纳的更彻底做法**：让 `block_meta` 直接以 FTS rowid 为主键并省掉该列（要改写入顺序，与差量写入的配对逻辑耦合）；`detail=`/`columnsize=`（查询侧是字面短语、需要位置）。

**它复核后确认的两条残余**（README 已如实标注）：① 正文现只以变形正文存在 FTS 内容表，读回靠 `joinCjk()` 逆变换，原文本身含 U+200B 的块无法 round-trip；② 变形让纯中文块的 FTS 内容表约翻倍。要省掉这份拷贝只能改 contentless FTS 并自建 snippet，代价大，不推荐。

## 已实现 4：体积与 pragma —— 补上收缩出口 ✅

**优化点**：库收缩出口此前**完全不存在**（全仓库 grep `vacuum|optimize|freelist` 零命中）。补 `compact()`：先 FTS5 `VALUES('optimize')`、再 `VACUUM`；并在 schema 版本不符就地重建后立刻回收一次。

**为什么两步都要**（侦察实测，367 真实会话/20.7MB 正文合成库）：
| 场景 | 结果 |
|---|---|
| 删掉最大的 30% 会话 | 31.535MB → **仍 31.535MB** |
| 再只 VACUUM | 14.180MB |
| optimize + VACUUM | **8.828MB**（差的 5.35MB 是 FTS 段内死空间；`fts_data` 7.008 → 1.676MB） |
| v3→v5 重建（DROP 后 0 行） | 文件仍 65.777MB → VACUUM 后 **0.070MB**（可回收 65.7MB） |

**落地**（`lib/store.js` + `lib/index.js` + `lib/monitor.js` + `lib/client.js`）：
- `compact({ vacuum })`、`shouldCompact()`（阈值 `dbBytes > max(4MB, textBytes × 1.6)`）、`pragmas()`（连接级 pragma 只能从本连接读）；
- 服务方法 `ctx.sessionBlockQuery.compact()`、面板「回收空间」按钮、`POST /session-blocks/compact`；
- 卸载时若该收缩则只做 optimize（不背 VACUUM 的独占与临时空间开销）；
- **WAL 静息体积**：`wal_autocheckpoint = 256` + `journal_size_limit = 1048576`（默认 1000 时静息 4.825MB → 1.000MB，每库省 3.8MB，写入耗时噪声内）。

**成本与风险**：optimize ≈4.7ms/MB、VACUUM ≈14ms/MB；VACUUM 不能在事务内跑、需 ~1× 临时空间、独占连接 → 只从关库/手动/重建路径调用。optimize 会先把文件撑大（30.77→35.40MB），必须紧跟页回收。

**实测掉的三个"别抄"**：`page_size=32768` → **+7.9%**；`synchronous`/`cache_size`/`temp_store`/`mmap_size` → 全在噪声内；external content → 我们正文只存一份，照搬**反而 +2.4%**。基线本身已紧：31.5MB / 20.7MB 正文 = 1.52×，FTS 占 88%。
**另一条重要澄清**：差量写入落地后，"抖动膨胀"已不是问题（原样再索引 Δ0.00MB、12 轮增长后 1.32×，optimize+VACUUM 只多回收 0.36MB）；这条优化的收益集中在**清理、缩水、重建**路径。

## 已实现 3：查询构造 —— 排序交给 FTS5 原生 rank ✅

**优化点**：`search()` 的 `ORDER BY bm25(block_fts) ASC, m.time DESC` 让 FTS5 无法消费排序，计划退成 `INDEX 0:M1` + `USE TEMP B-TREE FOR ORDER BY`，`LIMIT` 只能在全部命中物化之后生效；改成 `ORDER BY rank` 即拿到 `INDEX 32:M1` 的 top-N 路径。s-forge 的 `kernel/model/search.go:1960` 就是纯 `ORDER BY rank`（与同文件 `:1966-1984` 的 `CASE WHEN … END ASC, sort ASC, updated DESC` 并存，正说明差别在 ORDER BY 形状）。

**落地**（`lib/store.js`）：
- `ORDER BY rank`（FTS5 原生），投影里的 `bm25(block_fts) AS score` 保留；
- 当页取出后做一次 **JS 稳定重排**（`score asc, time desc`），把丢掉的跨表 tiebreak 补回页内，页内顺序与改造前一致；
- 新增 `block_meta(fts_rowid)` 索引（JOIN 探测走它，见下）；
- 去掉恒真的 `searchable = 1` 谓词（JOIN 出来的行必然有 `fts_rowid`）。

**实测**（`npm run bench:search`，40k 块 / 命中 2000 / 每页 21，node 22.19）：

| 形状 | 耗时 | 计划 |
|---|---|---|
| `ORDER BY bm25(…) ASC, m.time DESC` | 13.4ms | `INDEX 0:M1` + TEMP B-TREE |
| `ORDER BY rank` | 3.5ms | `INDEX 32:M1`,无临时 B 树 |
| `ORDER BY rank` 去掉 `fts_rowid` 索引 | 161.5ms | `SCAN m` |

侦察报告在 6 万块 / 1000 命中下测到 8.2s → 0.18s（47×），量级远大于我的 3.8×——差异来自语料与规模（它的 block_meta 行更宽）。两个方向都被证实：排序不再物化全量命中，且 JOIN 探测必须有索引兜着（否则每条命中全扫一遍元数据表）。

## 已实现 1：写入路径 —— 整会话重写 → 差量 + 追加快路径 ✅

**落地**（`lib/store.js`，schema 5 → 6）：
- 慢路径：与该会话已索引的块逐块对账——新块 INSERT、正文变了就地 `UPDATE block_fts SET text=? WHERE rowid=?`、只有展示性元数据变了就只 `UPDATE block_meta`、没变的块一行都不碰；判定用正文指纹（长度 + 约 53 位哈希，`textHash`）。
- **追加快路径**：`indexed_sessions` 存 `tail_seq` / `tail_digest` / `carry` / `config_key`；三者与"水位以下块数"都对得上就直接认定追加，老块既不读也不比，零元数据表读取。日志改写、块变少、块开关变化都会落回慢路径。
- `mode: "full"` 保留全量重写语义（内部测试与强制重建用）。

**实测**（`npm run bench`，每轮追加 1 块 × 10 轮取均值，node 22.19 + `node:sqlite`）：

| 会话块数 | 改造前（侦察基线） | 现在 | 提速 | 快路径命中 |
|---|---|---|---|---|
| 200 | 8.0ms | 0.21ms | 38.7× | 10/10 |
| 1000 | 32.3ms | 0.39ms | 83.4× | 10/10 |
| 3000 | 100.7ms | 0.43ms | 236.3× | 10/10 |

比侦察报告预估的 46× 更高：报告只算了"不重写倒排"，追加快路径把"读全部元数据行"也一并省掉了。
**代价**：冷启动更慢（拆字变换；3000 块约 63ms → 141ms）。**天花板仍在**：`indexer.js` 依旧 `readSession` 全量读 + `buildSessionBlocks` 全量抽块，端到端收益会被这层 JS 截顶——要再进一步就得让抽取也增量化（与"对账调度"那条一起做）。

## 已实现 2：中文召回 —— 存与查过同一个 CJK 拆字变换 ✅

**优化点**：`block_fts` 表结构不动，索引侧与查询侧对同一段文本做同一个「每个 CJK 字两侧插入零宽空格 `\u200b`」的变换，让 `unicode61` 把每个汉字切成独立词项且位置连续，原来的字面短语匹配自然升级为**任意 ≥1 字的中文子串召回**。这与 s-forge 的自定义分词器同构：它那边 `fts5SiYuanTokenize()`（go-sqlite3 fork 的 C 实现）也是逐码点出词项，`database.go:516-527` 的 `ftsTokenize()` 只是拼分词器名并固化在 `CREATE VIRTUAL TABLE` 里——所以"改了要重建索引"这条约束双方一致。

**落地**（`lib/store.js` 一个文件，schema 6）：`CJK_SEP` + `splitCjk`/`joinCjk` 两个纯函数 + 4 个写点（`insertFts`/`updateFtsText`）+ 1 个查询点 + 2 个读回点（`textOf` 的倒排分支、`snippet`）。`block_text` 那份是原文，不拆也不反拆。

**为什么不是别的**：trigram 在 1～2 字上恒为 0（且会让含 `OR` 的既有断言失效）；node:sqlite 只带内置分词器，JS 侧无法注册自定义分词器；双列方案召回一字不差却要多存一份原文（+83%～+118% 体积）。

**实测召回**（侦察，node 22.19 / SQLite 3.50.4）：1 字「答」0→2、2 字「回答」0→2、3 字「工作区」0→3；英文刻意不变（`ell` 仍 0、`hello` 仍 1）；必须逐字两侧隔离——只在相邻汉字间插分隔符时「工作」在 `🙂工作区`/`DSH工作区索引`/`第2个工作区` 上全为 0。

**代价**：索引体积 +14%（中英混排）～+71%（纯中文）；写入慢一些；精度从"整段等值"变"子串包含"（搜「苹果」也命中「苹果酱」，单字查询很宽）。

**测试影响**：落地后 9 文件 101 条全绿。唯一需要改的断言是 `incremental.test.mjs` 里"把正文改写成含原串前缀"那一条——子串语义下命中 1 条是正确的，已改成不含原串的改写文本。

## 侦察原文 1：写入路径（**已实现**，见上方"已实现 1"）

**优化点**：`store.replaceSession()` 改为按块差量：新增块批量 INSERT（显式 rowid）、变化块就地 `UPDATE block_fts SET text=? WHERE rowid=?` 后再更新 `block_meta`、消失块才删；未变块完全不碰。新块判定用 `SELECT MAX(seq) FROM block_meta WHERE session_id=?` 水位（`idx_block_meta_session(session_id, seq)` 支撑）。

**实测**（node 22.19 + node:sqlite，import 真实 `store.js`，每事件 10 块、追加 10 次取均值）：

| 会话块数 | 现状 A | 只批量化 B | 按块增量 C | FTS 重写行数（10 次追加） |
|---|---|---|---|---|
| 200 | 8.0ms | 8.4ms | 1.9ms | 2.5k → 0.1k |
| 1000 | 32.3ms | 33.4ms | 2.2ms | 10.5k → 0.1k |
| 3000 | 100.7ms | 91.5ms | 2.2ms | 30.5k → 0.1k |

A/C = 4.3× / 14.7× / 46×；**A/B ≈ 1.0–1.1×，只批量化几乎没用**——成本在整会话重分词与倒排维护，不在语句条数。事务数不变（1 次/会话）。

**s-forge 对应物**：`kernel/sql/upsert.go:446-473`（`queryBlockHashes` 求 `unChanges`，只送变化块）、`kernel/sql/block.go:138-168`（就地 `UPDATE blocks_fts ... WHERE rowid=?`；`block.go:116-117` 注明"先 FTS 后 blocks"的顺序约束）、`upsert.go:64-87`（512 分块批量）、`upsert.go:49-53`（external content 必须显式给 rowid）。

**改动面**：只动 `lib/store.js` 一个方法（约 80–150 行）。不加列无需重建；若加 hash 列则 schema 3→4 → 派生表 DROP 后下次对账全量重建一次。

**风险**：① cwd/title 等 meta-only 字段变化时未变块也要跟新；② `include` 或 config 变更要能触发一次全量重写；③ 流式会话同 seq 的块文本会增长，尾部必须走就地 UPDATE；④ 日志被压缩/改写要能识别并回退全量。
**天花板**：`indexer.js` 仍 `readSession` 全量读 + `buildSessionBlocks` 全量抽块（JS 侧 O(N)），端到端收益会被截顶，占比未测。
**待补测试**：① 只追加一个事件时未变块 `fts_rowid` 不变、generation 仍 +1；② 块数变少 / 末 seq 回退时残留块被删干净。

## 侦察原文 2：对账调度（**未实现**，等你定）

**优化点**：改为消费持久化脏集合（变更即入队 + 源侧便宜令牌比对）；全量校验只在启动做一次，空闲期做带冷却的订正。稳态下只有真变过的会话才读日志。

**为什么现在贵**：每轮 = `1×listSessions` + **`2×|plan|` 次整段日志装载**（`fetchTitles` 折标题一次、`listEvents` 算指纹一次，本轮真变的再 +1 次 `readSession`）。而 `|plan|` ⊇ 全部 live 会话（`indexer.js:75` live 每轮必进），冷会话每 `recheckMs`（默认 10min）各到期一次。即"判没变的代价等于把日志读一遍"。
公开契约里没有便宜信号：`SessionRecord` 只有 `{header, live, persisted}`（`packages/session-query/session-query/src/types.ts:27-34`）；官方 provider 反而拿 `persistence` 的 opaque revision 比对，没变就 `continue`（`session-query-sqlite/src/index.ts:411,514`）。

**改后**：每轮 = 1×列表 + O(1)/会话令牌比对 + 仅脏会话 1 次装载（标题与正文共用一次）。稳态无变更的一轮 = 日志装载 0 次（现 2|plan|）。

**s-forge 对应物**：`kernel/sql/index_queue.go:70-102`（变更当场落盘成一行 JSON + flock）、`:237-258`（启动 `recoverIndexQueue` 重放）、`:137-166`（`clearIndexQueue(snapshotSize)` 只留快照之后）；`kernel/model/index_fix.go:62-74`（`checkIndex` 用 sync.Once 只做一次全量校验）、`:112-143`（`AutoFixIndex`：空闲 ≥7min + dirty + 冷却 ≥120min + TryLock 抢不到就跳过）。
**DSH 侧现成入口**：`session/event` 是 post-commit append feed（`packages/core/session/src/index.ts:61-72`）。

**改动面**：`indexer.js`（plan → 脏集合 + 令牌）、`runner.js`（触发合并成一轮）、`index.js`（注入 `sessionPersistence`、订阅 `session/event`、启动触发一次校验）、`store` 加一对簿记（令牌 + 待办）。
**风险**：① `sessionPersistence` 是可选服务，拿不到要退回指纹轮；② revision 只同实例可比（`session-persistence/src/index.ts:181-186`），重启须按"全都可能变了"处理；③ `session/event` 是 Scoped 广播且 observer 失败被吞，漏一次就退化为"下次全量校验才发现"，故全量校验不能省；④ live 会话可能未落盘，这条腿靠 append 事件而非 revision。
**顺带发现**：`fetchTitles` 对每个 planned 会话整段读一次日志折标题，而库里（`indexed_sessions.title`）已经存了标题——索引路径却没看它。
**待重写测试**：`indexer.test.mjs:111-127 / :147-165 / :167-192`、`async.test.mjs:69-83`（`readSession=6` 那条）。

## 两条的关系（写入那条已落地，调度那条待定）

写入那条主张"**少写**"已经做完（差量 + 追加快路径）；调度那条主张"**少读**"还没做（现在每轮仍是 `1×listSessions + 2×|plan|` 次整段日志装载）。两者不冲突：
