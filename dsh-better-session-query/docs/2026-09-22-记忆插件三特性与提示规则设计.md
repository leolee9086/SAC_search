## 一、遗忘事件（已定案）

**做法**：往会话日志推一条 tool-call 事件，工具名固定（如 `memory_forget`），参数是 block_id，而**这个工具不在任何 agent 的工具表里**。

为什么成立：
- DSH 认识它（普通 tool-call，不需要新事件类型，不用操心 required-on-read）
- **agent 产生不了它** —— agent 的能力边界不是「能写日志」而是「能调工具」，事件都是工具产生的
- 人能产生（往 JSONL 追加一行，或者一个只挂人这边的 CLI / GUI 动作）
- **遗忘集合仍然从日志派生** —— 索引器 fold 出集合，重建时重算，不引入第二真相源
- 不重写任何已有事件，append-only 完好

这是「时间折叠」范式的又一例：一个真相源（会话日志），多个 fold 视图。块索引是全量 fold，记忆库是抽特定工具调用的 fold，遗忘集合是抽遗忘事件的 fold，intent 库是按时间叠加指令的 fold。

人侧入口待定：默认 zstd 压缩手改不了，要么配 `compression: 'none'`，要么给一条只挂人这边的命令。

## 二、按 preset 隔离记忆（待实现）

**前提已查清**：会话日志头部有 `header.agentPreset`，每次切换记一条 `agent-preset/selected` 事件（见 `agent-presets/src/types.ts`）。所以「这条记忆是哪个 preset 的」不用另存 —— 抽块时按事件顺序跟一遍就知道，而且是**写下那条记忆时的 preset**，不是会话现在的 preset。

设计：
- 记忆表加一列 `preset`
- recall 默认按调用方会话的 preset 过滤（调用方 preset 同样从头部 + 最后一条 selected 拿）
- **全局记忆权限**是会话级开关 —— 待定：开关本身也是状态，存哪、谁能写。agent 能自己开的话隔离就形同虚设；要人来开就还得一条人能产生的通道（跟遗忘事件同一个路子）
- 旧记忆没有 preset，得定默认（收还是不收）

## 三、提示规则（跨插件，互不依赖）

**分工（哥哥纠正过，我一开始搞反了）**：
- **索引插件只给规则** —— `ctx.provide` 一个纯数据对象，它不知道谁在读，也不判断谁该提示
- **context_care 负责判断和发起** —— `ctx.get` 取规则，取不到就什么都不做；它自己监听 `agent/pre-step` 和 `agent/assistant-stream`，inject 里有 `agents` 和 `sessionProjections`，会话和事件都摸得到，记「上次 remember 是什么时候」没问题
- 命中后走它已有的 `agent.inject(notice(...))` 机制

### 规则形状

纯数据，不带函数（跨插件传函数既不能序列化也没法检查）。

```js
{
  id: 'memory-idle',       // 必填
  order: 10,               // 必填：优先级，规则可能来自多处，声明顺序不算数
  placement: ['user'],     // 对哪些位置生效
  when: { ... },
  action: {
    kind: 'notify',
    by: 'context-care',
    say: '……',            // 提醒文案。模板渲染（{args.path} / {tool} / {time}）还没做
  },
  cooldownMinutes: 0,      // 冷却管时间；明确指令类的规则不该被时间挡住
  oncePerSurface: true,    // 去重管内容：同一段 surface 上只提醒一次
}
```

`when` 四种形状（**同一对象里的字段是 AND，OR 靠写两条规则**）：

```js
{ tool: 'read' }                                            // 调用了某个工具
{ tool: ['a', 'b'] }                                        // 其中任意一个
{ tool: 'read', args: { path: '.md' } }                     // 参数名 → 子串
{ tool: 'read', args: { path: ['D:/dev/src', '.js'] } }     // 数组 = 都要包含
{ idle: { since: 'session_blocks_remember', minutes: 10 } } // 一段时间没调用它
{ said: '关键词' }                                           // 用户说了这段文字
{ produced: '模式' }                                         // 助手输出里有这段文字
```

`args` 用「参数名 → 子串」是因为工具调用的参数本来就在事件里，这样任何工具的任何参数都能匹配，不用为每种工具单加字段。

**匹配先只做子串，不引入正则** —— 跨插件传正则既没法序列化也挡不住 ReDoS，这四种情况用子串都表达得了。

**冷却 vs surface**：冷却管时间间隔，surface 管当前上下文里有没有，是两回事，要分开表达。

### 规则引擎：用 @leolee9086/dsh-rule-engine（2026-09-22 当天改的口）

上面那版判断「自己写几十行」是在**只有这一个用例**的前提下做的。
当天下午哥哥让我把规则引擎实现成一个独立库 —— 因为它要服务的不只是记忆提醒，
还有上下文清洗、隐私清洗、前缀缓存预算那一整套（见 `D:\dev\dsh-rule-engine\`）。
既然库已经在做，这里就没有理由再自己写一份。

分工不变，只是中间多了一层：**本插件仍然只给纯数据规则**，
`ctx.provide('memoryNoticeRules', NOTICE_RULES)`，不知道谁在读；
context_care 取这个服务、接进引擎、命中后注入。

规则形状按引擎的规范补了两个字段：`order`（优先级，必填）和 `action.say`（提醒文案）。

### 原来的判断（留档）

搜到的：`json-rules-engine`（CacheControl，最主流）、`json-rules-engine-upgraded`（自称 TS 优先的维护继任者）、`json-logic-engine`（纯表达式求值）。

**判断是不用**：规则引擎解决的是「业务规则多变 + 条件组合复杂 + 冲突要解决」（Drools 那一类）。我们的条件形状固定、全是 AND、子串匹配，自己写几十行。真正的工作量在引擎管不着的地方 —— 冷却、surface 去重、模板渲染、跟事件流对接 —— 引了也省不掉，而 DSH 的规范要求依赖得真的删掉自己本来要写的代码和测试。

**健壮不从依赖来，从测试来**：冷却边界、surface 去重、模板缺字段、规则是坏数据，这些得一条条覆盖。

以后条件真复杂到要嵌套 OR / 比较 / 正则，再引 `json-logic-engine` 这类只做求值的库也不迟。

## 四、实施顺序与测试

顺序：**先做 preset 隔离**（它动 schema，另外两个都建在这张表上）→ 遗忘事件 → 提示规则。

测试：那个插件**不能用 `node --test`**（会 EPERM），逐个跑 `node test/xxx.test.mjs`。每个特性各配一组 —— preset 隔离测跨 preset 互不可见加开关生效；遗忘测 fold、过滤、以及重建后遗忘还在；提示规则测取不到服务时的降级。
